In 2026, every engineer I know is running multiple coding agents in parallel. The agent doing UI work in one terminal, the one doing the migration in another, the one fixing a bug in a third. They're all on the same repo, all wanting to run dev servers, hit a database, run tests.

The naive setup falls over fast. Two agents try to bind to port 3000. One runs a migration the other's tests aren't expecting. The Stripe webhook listener you started for one agent fires events into the database another agent is reading. It's two cooks in the same kitchen. Productive in theory, chaotic in practice.

I solved this for LeadSwitchboard. Each agent gets its own git worktree, its own pair of dev ports, and its own isolated copy-on-write Postgres branch on Neon. Bring-up is one command. The agents never collide. Here's how it works.

## The problem in detail

The shared-resource collisions are obvious once you start running agents:

- **Port collisions.** Both Next.js and FastAPI default to fixed ports. Two agents starting dev servers fight for the same port. One wins, the other crashes, the agent tries the next port, and now you have config drift.
- **Database collisions.** Even if both agents only read, one might run an autogenerate migration on a feature branch and leave the schema in a state the other isn't expecting. If both agents run migrations, your local DB schema is whichever one landed last.
- **Filesystem collisions.** Two agents writing to `node_modules/` at the same time is asking for trouble. Two agents regenerating Prisma clients at once produce a non-deterministic mess.
- **Webhook collisions.** Stripe and the CRM webhook tunnels both terminate at one ngrok URL. Another agent's backend processes events fired during one agent's test run.

Each of these has an ad-hoc fix. None has an ergonomic one. Isolating the system is the only answer that scales past two agents.

## Worktrees as the isolation unit

Git worktrees are the right unit. A worktree is a separate filesystem checkout of the same repo, on its own branch, sharing the `.git` directory and history. They're cheap and instant to create.

The structure I converged on:

```
~/apps/platform/                    ← main checkout
~/apps/platform/.claude/worktrees/
  feature-a/                        ← worktree on branch feature-a
  bugfix-b/                         ← worktree on branch bugfix-b
  spike-c/                          ← worktree on branch spike-c
```

Each worktree has its own filesystem, so its own `node_modules`, its own `.next/` build cache, its own everything-derived-from-source. They share git history and `.gitignore`, so untracked working-tree state from one doesn't pollute another.

Creating one is a single command:

```bash
claude -w feature-a
```

This creates the worktree if it doesn't exist, switches the agent into it, and gives it a clean tree.

## Deterministic port allocation from the worktree path

Parallel agents work without configuration because the script computes dev ports deterministically from the worktree's path.

```bash
# Hash the worktree path into a stable port range
hash=$(echo "$PWD" | shasum -a 256 | head -c 4)
fe_port=$((3100 + 0x$hash % 100))
be_port=$((8100 + 0x$hash % 100))
```

The same path always hashes to the same ports, so each worktree gets a stable, collision-resistant pair. No `.env` editing, no remembering which agent is on which port. Open the worktree, run the dev script, see your ports.

The script writes the ports to a file the frontend reads for its API base URL:

```
NEXT_PUBLIC_API_URL=http://localhost:8147
```

And it prints the URLs at startup so the agent can verify them:

```
Frontend: http://localhost:3147
Tenant:   http://demodev.localhost:3147/admin/leads
```

Because the platform is multi-tenant on subdomain (`<agency>.leadswitchboard.io`), the dev URL uses `*.localhost` resolution, which most browsers handle without `/etc/hosts` edits.

## The Neon piece: copy-on-write branches per git branch

Ports solve compute isolation. Database isolation is the harder problem.

Neon has a feature that fits this: **branches**. A Neon branch is a copy-on-write snapshot of the parent database. Creating one is close to free, since Neon copies no data until the branches diverge. They're isolated, so writes to one branch don't affect the other. They're full Postgres, so you can connect to them like any other DB.

The dev script wires this in:

```bash
# Map the git branch to a Neon branch name
git_branch=$(git rev-parse --abbrev-ref HEAD)
neon_branch="dev-$git_branch"

if ! neonctl branches list --project-id "$NEON_PROJECT_ID" \
     | grep -q "$neon_branch"; then
    # First run for this git branch — create the Neon branch
    neonctl branches create --name "$neon_branch" \
        --project-id "$NEON_PROJECT_ID"
    
    # Get the connection string and run migrations
    export NEON_PLATFORM_DATABASE_URL=$(
        neonctl connection-string "$neon_branch" \
            --project-id "$NEON_PROJECT_ID"
    )
    alembic upgrade head
else
    # Branch exists — reuse it, no migration needed
    export NEON_PLATFORM_DATABASE_URL=$(
        neonctl connection-string "$neon_branch" \
            --project-id "$NEON_PROJECT_ID"
    )
fi
```

Every git branch now has its own Postgres database that starts as an exact copy of the parent and diverges as the agent works. Migrations on one branch don't touch any other. Test data from one agent's test run doesn't appear in another agent's database.

When the agent merges and the worktree gets cleaned up, I delete the Neon branch by hand. Automatic cleanup is a known gap.

## The full bring-up sequence

On first run for a new branch, `worktree-dev.sh` does this:

1. Source environment from `.zshrc` (which has Neon API keys, Clerk keys, etc.)
2. Compute deterministic ports from `$PWD`
3. Check if `node_modules` exists; install if not
4. Check if Neon branch `dev-<git-branch>` exists; create + migrate if not
5. Export `NEXT_PUBLIC_API_URL` and `NEON_PLATFORM_DATABASE_URL`
6. Start the FastAPI backend on the computed port
7. Start the Next.js frontend on the computed port
8. Print the tenant URL

Total time on a fresh worktree: about 30 seconds (mostly `npm install`). On a returning worktree: about 5 seconds.

The agent can then run tests, hit the API, see the UI, and generate migrations without worrying whether another agent is touching the same state.

## The migration-conflict edge case

Parallel agents can still trip over each other in one place: Alembic autogenerated migrations.

If two agents add migrations to the same parent revision, you get two heads. The merge looks like:

```bash
# In whichever worktree merged second
alembic merge heads -m "merge feature-a and bugfix-b"
alembic upgrade head
```

I documented this in CLAUDE.md so agents know to handle it. In practice it happens maybe once every couple of weeks. The fix is mechanical and the script can detect and prompt for it.

## What this unlocks

Full isolation is what makes this worth it:

- **Parallel feature work.** Two agents shipping unrelated features need no coordination. They have different ports, different databases, different filesystems.
- **Realistic testing on real-shaped data.** Each Neon branch is a full snapshot of the parent, so test data isn't synthetic. Bugs that only show up with real data shapes surface at dev time.
- **Per-branch Vercel previews.** Push the worktree branch and Vercel deploys a preview against that branch's database (via env var injection at deploy time). The branch is reviewable end-to-end without merging anything.
- **Cheap rollback.** If an agent's experiment goes sideways, the worktree is disposable: code, branch, and Neon DB. No "I broke my local DB" recovery work.
- **Reproducible bug reports.** A bug found on `feature-a` is reproducible because the database state is preserved. No "works on my machine" because every machine's machine is the same machine.

## What I'd do differently

**Build automatic cleanup from day one.** Branches accumulate. Neon doesn't charge much for branch storage, but the list gets unwieldy past 30-40 branches. A nightly job that deletes Neon branches whose git branch was merged or deleted would have saved a lot of manual `neonctl branches delete` calls.

**Use Neon branch IDs, not names.** I keyed branches off git branch names because they're human-readable. Branch names with slashes (`feature/foo-bar`) and special characters caused problems early on. Hashed names with the human name in metadata would have been more robust.

**Add a port-conflict guard.** The hash function has a small but nonzero chance of mapping two paths to the same ports. I never hit it, but the script doesn't warn if it happens. A check-before-bind step would be cheap insurance.

**Pre-warm node_modules in a shared cache.** Each worktree runs its own `npm install`. A shared package cache via pnpm or yarn berry would make the first bring-up faster.

## The bigger lesson

Tools designed for one human at one desk on one branch don't fit. The first thing to break is shared mutable state: ports, databases, environment variables. The human conventions ("I'll start the backend, you wait") don't translate.

The fix is more isolation, not more discipline. Worktrees + deterministic ports + branch databases give each agent the equivalent of its own development environment without the cost of maintaining N of them.

If you're running parallel agents and coordinating around shared resources, the tools to fix it already exist. Combine them and the agents stop colliding.
