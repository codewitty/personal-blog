In my previous post, [Efficient error handling in Go](/blog/error-go), I covered the basics of Go's error handling. This post covers advanced techniques that give you more control and make debugging easier.

## 1. Defer error handling with recover

To recover from a panic and handle the error cleanly, use recover together with defer:

```go
func dangerousOperation() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Recovered from panic:", r)
        }
    }()

    // Perform some operation that might panic
    // ...
    panic("something went terribly wrong")
}
```

## 2. Use the "errors" package for sentinel errors

The "errors" package lets you define sentinel errors, predefined error values that callers can compare for equality:

```go
var ErrNotFound = errors.New("not found")  // Sentinel error

func findUser(id int) (*User, error) {
    // ... code to find user
    if user == nil {
        return nil, ErrNotFound
    }
    return user, nil
}
``` 

## 3. Wrap errors for better context

When returning errors from lower-level functions, wrap them with context. Since Go 1.13 the standard library does this with the `%w` verb in fmt.Errorf, and callers can still match the original error with errors.Is or errors.As:

```go
func someFunc() error {
    if err := someOtherFunc(); err != nil {
        return fmt.Errorf("someFunc failed: %w", err)
    }
    return nil
}
```

The third-party github.com/pkg/errors package offers errors.Wrap, which does the same and also records a stack trace:

```go
import "github.com/pkg/errors"

func someFunc() error {
    if err := someOtherFunc(); err != nil {
        return errors.Wrap(err, "someFunc failed")
    }
    return nil
}
```

## 4. Add a message without a stack trace

github.com/pkg/errors also has errors.WithMessage, which adds context to an error without recording a stack trace:

```go

func someFunc() error {
    if err := someOtherFunc(); err != nil {
        return errors.WithMessage(err, "someFunc failed")
    }
    return nil
}
```

## Conclusion

Try these techniques in your own projects. The more you use them, the more natural robust error handling in Go becomes.
